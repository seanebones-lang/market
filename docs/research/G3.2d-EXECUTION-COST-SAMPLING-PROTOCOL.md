# G3.2d Prospective Robinhood v2 Execution-Cost Sampling Protocol

- **Protocol ID:** `rh-v2-cost-sampling-v1`
- **Protocol version:** 1.0
- **Frozen:** 2026-08-17T23:41:01Z
- **Status:** Sampling and analysis decisions frozen; no dated run authorized or started
- **Input contract:** G3.2c execution-cost observation schema version 1
- **Strategy role:** Strategy-agnostic input to a future G3 protocol 2.0
- **Broker contact authorized here:** None
- **Credential authorized here:** None
- **Order or execution authorized here:** None

## Purpose

G3.2c defined one strict, sanitized cost observation. G3.2d freezes how a future corpus of those
observations must be scheduled, admitted, summarized, and translated into candidate backtest cost
inputs before any real route data is seen.

This prevents the cost study from changing its cadence, quantities, missing-data rules, quantiles,
or base/stress mapping after favorable or unfavorable values appear. The study contains no EMA
field, strategy result, market-return result, G1 candle, or holdout access.

The machine-readable protocol is
`config/research/rh-v2-cost-sampling-v1.json`. Its invariant decisions are frozen, but collection
cannot begin from that file alone. A separate dated run plan must bind an explicitly authorized
future window to the exact protocol SHA-256 before the first scheduled observation.

## Official endpoint constraint used by the design

Robinhood's official v2 estimated-price endpoint accepts `side=both`, supports comma-separated
quantities, and allows at most ten quantities in one request. Its quantity-aware bid and ask
prices exclude the fee, while its response separately provides fee ratio, estimated fee, and
estimated total cost or credit. The best-price endpoint represents partner-exchange prices and
does not account for order size or fee.

The protocol uses four quantities in one estimated-price request, below the official limit:

```text
0.00025 BTC
0.00050 BTC
0.00100 BTC  primary research quantity
0.00200 BTC
```

Official reference:
[Robinhood Crypto Trading API documentation](https://docs.robinhood.com/crypto/trading/).

## Fixed sampling schedule

One valid run covers exactly 30 complete UTC dates.

| Decision | Frozen value |
|---|---:|
| Duration | 30 complete UTC days |
| Interval | 900 seconds / 15 minutes |
| Offset | 420 seconds after UTC midnight |
| Scheduled minute marks | `07`, `22`, `37`, `52` |
| Cycles per hour | 4 |
| Cycles per UTC day | 96 |
| Expected complete cycles | 2,880 |
| Quantities per complete cycle | 4 |
| Expected quantity observations | 11,520 |
| Maximum final-response lateness | 60 seconds after the scheduled slot |
| Early capture | Forbidden |
| Window extension | Forbidden |

The seven-minute offset avoids mechanically sampling exactly at hourly signal-bar boundaries while
retaining uniform coverage of every UTC hour. The first slot must be `00:07:00Z` on the first date;
the last slot is `23:52:00Z` on day 30. The run end is the following date at `00:07:00Z`, exclusive.

The future collector should obtain, inside the G3.2c 60-second capture envelope:

1. accounts and fee tier;
2. the BTC-USD trading pair;
3. BTC-USD best bid/ask; and
4. one `side=both` estimated-price response containing all four quantities.

The one multi-quantity response is deterministically split into four G3.2c bundles sharing the same
account, pair, displayed book, and per-endpoint receive timestamps. A cycle is complete only when
all four bundles verify and share one capture signature.

No collector, request signer, credential loader, network client, or retry policy is implemented by
G3.2d.

## Two-stage freeze and authorization

The invariant protocol and the dated run plan are deliberately separate.

A valid run plan must contain:

- the exact protocol ID, version, and SHA-256;
- a path-safe run ID;
- a nonempty authorization reference;
- its own UTC freeze timestamp;
- the first scheduled slot;
- the exact 30-day exclusive end; and
- exactly 2,880 expected cycles.

It fails unless:

- its freeze time is at or after the protocol freeze time;
- its freeze time is before collection starts;
- the start is the first configured slot of a UTC date; and
- its protocol hash and all schedule-derived fields match.

No production run plan is committed. Writing a run plan is an offline action and does not prove
that its authorization reference is valid. Human authorization and credential scope remain
external prerequisites.

## Structural corpus admission

Every input manifest is reverified under G3.2c before aggregation. Analysis aborts on:

- a checksum, byte-count, redaction, schema, or deterministic-rederivation failure;
- a synthetic source in a production run;
- a symbol or quantity outside the protocol;
- a duplicate observation ID;
- duplicate quantity evidence in one scheduled cycle;
- an observation outside the fixed window or more than 60 seconds late;
- a partial observation that cannot map to exactly one expected slot; or
- quantity bundles in one allegedly complete cycle that do not share account tier, pair contract,
  displayed book, and endpoint receive times.

Partial cycles are retained in failure evidence but are not admitted to any cost distribution.
All quantity distributions therefore use the same set of complete timestamps.

## Coverage and missing-data contract

The fixed 30-day window is never extended to replace missing or inconvenient observations.
Coverage uses complete four-quantity cycles, not individual response rows.

The corpus passes only if all of these hold simultaneously:

| Coverage rule | Required minimum |
|---|---:|
| Overall scheduled-cycle coverage | 90% |
| Coverage inside every represented UTC hour | 80% |
| Coverage inside every represented UTC weekday | 80% |
| UTC dates with at least one complete cycle | 30 of 30 |

If any rule fails, the summary is still preserved with explicit failure reasons, missing slots,
and partial-cycle quantities. Base and stress cost profiles are withheld. There is no imputation,
forward fill, interpolation, selective rerun, or optional window extension.

HTTP errors, rate limits, timeouts, clock failures, malformed responses, and local outages in a
future collector must become missing scheduled cycles or structured failure events. They must not
be silently replaced by a later off-schedule observation.

## Prespecified descriptive measures

For every quantity, complete cycles report exact-Decimal distributions for:

- midpoint USD;
- displayed full spread bps;
- fee bps per fill;
- buy and sell size impact from the displayed touch;
- buy and sell all-in one-way cost from midpoint;
- indicative round-trip cost from midpoint;
- capture span seconds; and
- maximum estimated-price age seconds.

Every distribution retains count, minimum, arithmetic mean, maximum, and nearest-rank p50, p75,
p90, p95, and p99.

## Daily-block uncertainty

Each reported quantile also receives a deterministic 90% daily-block bootstrap interval:

```text
block = one complete UTC date
replicates = 999
seed = 20260817 plus a stable metric-specific SHA-256 salt
interval = nearest-rank 5th and 95th percentiles of bootstrap estimates
```

Sampling whole UTC dates preserves intraday dependence inside each day. The intervals describe
sampling variation within this 30-day observation design; they do not establish stationarity or
guarantee that future execution costs follow the same distribution.

## Prespecified backtest-input mapping

Only the primary `0.001 BTC` quantity maps to candidate engine inputs. Other quantities describe
size sensitivity.

For each profile:

```text
transaction fee per fill = maximum observed fee bps
quoted full spread = configured quantile of displayed full spread
observed size impact = max(0, buy size-impact quantile, sell size-impact quantile)
adverse slippage = observed size impact + explicit unmeasured-execution buffer
additive round trip = 2 * fee + full spread + 2 * adverse slippage
```

| Profile | Component quantile | Unmeasured execution buffer per side |
|---|---:|---:|
| Base candidate | p75 | 10 bps |
| Stress candidate | p95 | 20 bps |

Using the maximum observed fee avoids assuming that a temporary lower fee tier persists. Taking
the worse directional size-impact quantile avoids averaging away a one-sided depth problem.
Clamping size impact at zero prevents price improvement from offsetting the explicit execution
buffer.

These outputs are labeled
`candidate_research_input_not_execution_evidence`. They are not actual fills, realized slippage,
or automatic protocol 2.0 assumptions. A successor study must explicitly adopt or reject them
before strategy evaluation.

The additive round-trip number is a readable diagnostic, not the engine's exact multiplicative
flat-price return. Any adopted profile must still be replayed through the production fill and fee
arithmetic.

## Immutable analysis evidence

The offline analyzer writes:

```text
rh-v2-cost-study-RUN_ID-<16 hex>/
  manifest.json
  summary.json
  corpus.json
```

The corpus binds every G3.2c observation ID, scheduled and received time, quantity, evidence
manifest SHA-256, and observation SHA-256. The study ID is recomputed from both the complete summary
and sorted corpus bindings. Verification checks file hashes and byte counts, strict schemas,
identity fields, corpus count, and the content-addressed study ID. Existing directories are never
overwritten.

## Offline commands

The following commands contain no collection or broker transport:

```bash
# Do not run for production until a real authorization reference and future window exist.
./market.sh freeze-rh-v2-cost-run \
  --protocol config/research/rh-v2-cost-sampling-v1.json \
  --start FUTURE_DATE_T00:07:00Z \
  --frozen-at FREEZE_TIMESTAMP_Z \
  --authorization-reference APPROVAL_RECORD \
  --out PATH_TO_IMMUTABLE_RUN_PLAN.json

./market.sh summarize-rh-v2-cost-study \
  --protocol config/research/rh-v2-cost-sampling-v1.json \
  --run-plan PATH_TO_IMMUTABLE_RUN_PLAN.json \
  --observations-root PATH_TO_G3_2C_BUNDLES \
  --out-dir data/research/execution-cost-studies

./market.sh verify-rh-v2-cost-study \
  --manifest data/research/execution-cost-studies/SUMMARY_ID/manifest.json
```

The summarize command returns a nonzero status after preserving evidence when coverage admission
fails.

## Limitations and stopping boundary

- Thirty days may not represent other volatility, liquidity, price, or fee-tier regimes.
- Estimated prices are hypothetical and cannot identify realized execution slippage.
- Uniform clock sampling may not match the conditional times at which a future strategy trades.
- Fixed BTC quantities change in dollar notional as BTC price changes.
- The sample is account- and route-specific and must not be generalized to v1 market-maker
  routing.
- A later API or fee-schedule change requires a new protocol version.

G3.2d completes prospective sampling and offline analysis design only. No production run plan,
credential, signature, request, observation, strategy result, or live-money permission exists.
G3.3, G4, and G5 remain paused or locked.
