## Purpose

Resolve the contradiction between Robinhood's published v2 best-price field definitions and the
live G3.2e preflight without changing the frozen execution-cost estimand after endpoint contact.
This plan authorizes documentation and offline preparation only. It does not authorize another API
request, a support-ticket submission, diagnostic collection, production scheduling, an order, or
capital use.

## Facts fixed before this plan

Robinhood's official v2 component schema defines:

- `bid`: the best price partner exchanges provide for a sell order; and
- `ask`: the best price partner exchanges provide for a buy order.

The G3.2c observation contract therefore requires `ask >= bid`. The first authenticated preflight
attempt exposed only one schema difference: an undocumented best-price `timestamp`. A pre-results
compatibility amendment now admits that one optional UTC field while excluding it from persistence
and derivation. Two subsequent attempts then stopped because the live row had `ask < bid`.

No price, spread, fee, response body, account identifier, buying power, credential, or strategy
output was logged or persisted. The estimated-price request was never reached, the preflight output
directory remained absent, and the 30-day production schedule was not created.

Official source:

- [Robinhood Crypto Trading API documentation](https://docs.robinhood.com/crypto/trading/)

## Interpretation that remains frozen

Let `B` be the API field labeled `bid` and `A` the field labeled `ask`.

```text
sell touch = B
buy touch = A
displayed midpoint = (A + B) / 2
admissible row requires A >= B
```

The project must not swap the fields, replace them with `min(A, B)` and `max(A, B)`, take an
absolute spread, clip a negative spread to zero, select a later favorable quote, or call a crossed
row an execution-cost observation. Any such change would alter the estimand after live contact.

5. Secret, account-identifier, buying-power, schema, tradability, timestamp, arithmetic, and

A support reply alone does not pass G3.2e. A coherent one-off quote alone does not pass G3.2e. The
ordinary four-resource preflight must still pass under the unchanged contract.

## Fallback: sign-only prospective diagnostic

The fallback is not currently authorized or implemented. It requires a new identifier-bearing
authorization record before code, scheduler installation, or network contact.

### Fixed design

- **Endpoint:** `GET /api/v2/crypto/marketdata/best_bid_ask/?symbol=BTC-USD`
- **Duration:** two complete UTC days
- **Cadence:** every 15 minutes
- **Scheduled slots:** 192
- **Admission window:** scheduled instant through 60 seconds late, inclusive
- **Retries:** none
- **Backfill:** none
- **Other endpoints:** none
- **Orders, holdings, order history, transfers:** forbidden

Each claimed slot may persist only:

- protocol version and future authorization reference;
- scheduled UTC slot and local UTC receive time;
- HTTP outcome category without body text;
- result-row count and matching-symbol count;
- presence and UTC-validity category of the optional timestamp;
- one relation category: `ask_lt_bid`, `ask_eq_bid`, or `ask_gt_bid`; and
- immutable file hashes.

It must never persist either price, price difference, midpoint, spread magnitude, response body,
account number, buying power, API key, signature, private/public signing key, authorization header,
fee, estimated price, holding, order, fill, or transfer.

### Fixed decision rule

The diagnostic is interpretable only with at least 183 completed slots, corresponding to 95%
coverage. It resolves the operational contradiction only if all completed, structurally valid rows
have `ask_eq_bid` or `ask_gt_bid` and zero have `ask_lt_bid`. Zero crossings in at least 183 rows
places the conservative rule-of-three upper bound below 1.64%, leaving margin under the production
protocol's 5% incomplete-cycle allowance.

Any crossed row, coverage failure, unknown field beyond the admitted optional timestamp, symbol
mismatch, pagination, malformed timestamp, authentication failure, or evidence-integrity failure
leaves G3.2e blocked. The sample must not be extended, retried, filtered, or restarted to obtain a
favorable outcome.

The diagnostic cannot set a transaction-cost value, validate a strategy, or substitute for the
ordinary four-resource preflight.
