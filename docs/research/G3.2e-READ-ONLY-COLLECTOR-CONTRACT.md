# G3.2e Authorized Robinhood v2 Read-Only Collector Contract

- **Authorization:** `AUTH-G3.2E-RH-READONLY-2026-08-17`
- **Status:** Implementation ready; credential registration and broker preflight pending
- **Target protocol:** `rh-v2-cost-sampling-v1`
- **Target symbol:** `BTC-USD` only
- **HTTP methods:** `GET` only
- **Capital authorization:** None
- **Order authorization:** None

## Purpose and boundary

G3.2c defined one sanitized cost observation, and G3.2d prospectively froze how 30 days of those
observations must be scheduled and analyzed. G3.2e implements the smallest authenticated,
read-only path capable of producing those inputs.

This is a narrow, identifier-free authorization exception recorded in
`docs/authorizations/2026-08-17-g3.2e-robinhood-read-only.md`. It does not unlock the general G5
broker adapter and does not authorize a strategy, an order, a transfer, a holdings change, or live
capital.

## Credential scope and lifecycle

The Robinhood credential must enable only:

- Read crypto accounts;
- Read crypto products; and
- Read crypto quotes.

Neither Robinhood order action may be enabled. Holdings and order-history reads are unnecessary
for this cost study and are excluded.

Credential material never comes from environment variables, `.env`, command-line arguments,
repository files, fixtures, logs, evidence, or chat. Two local commands divide key preparation
from Robinhood registration:

```bash
./market.sh prepare-rh-readonly-key --credential-label g3-cost-study-v1
./market.sh complete-rh-readonly-credential --credential-label g3-cost-study-v1
```

The first command:

1. generates an Ed25519 signing seed with PyNaCl;
2. stores the private seed through the macOS Keychain backend;
3. stores the corresponding public key for pair-consistency checking; and
4. prints only the public key and its SHA-256 fingerprint.

The account owner registers that public key in Robinhood web classic and selects the three allowed
read actions. Robinhood then issues an API key. The second command obtains that API key from a
hidden interactive prompt and stores it in macOS Keychain. It has no `--api-key`, `--private-key`,
or secret-file option.

`show-rh-readonly-public-key` can re-display the public value. `check-rh-readonly-credential`
derives the public key from the stored private seed and verifies a local sign/verify challenge. No
credential command contacts Robinhood or prints a secret.

The software can verify key-pair consistency and successful access to the allowed endpoints. The
Robinhood response does not independently attest which actions were selected in the website.
Therefore the account owner must visibly confirm the action list during registration. Any doubt
about scope requires disabling the credential and creating a replacement.

## Authentication contract

Robinhood requires `x-api-key`, `x-signature`, and `x-timestamp`. The signature is Ed25519 over:

```text
api_key + unix_timestamp + request_path_with_query + HTTP_method + body
```

The client signs bodyless `GET` requests only. The published Robinhood signature vector is retained
as a byte-for-byte test of the primitive. Every real request obtains a fresh UTC Unix timestamp and
is issued immediately after signing.

Official references:

- [Robinhood Crypto Trading API documentation](https://docs.robinhood.com/crypto/trading/)
- [Robinhood Crypto API setup](https://robinhood.com/us/en/support/articles/crypto-api/)

## Exact network allowlist

The public client has four methods and no generic request method:

| Method | Path | Allowed query keys |
|---|---|---|
| `GET` | `/api/v2/crypto/trading/accounts/` | none |
| `GET` | `/api/v2/crypto/trading/trading_pairs/` | `symbol` |
| `GET` | `/api/v2/crypto/marketdata/best_bid_ask/` | `symbol` |
| `GET` | `/api/v2/crypto/trading/estimated_price/` | `symbol`, `side`, `quantity` |

The client additionally fixes:

- origin `https://trading.robinhood.com`;
- symbol `BTC-USD`;
- estimated-price side `both`;
- one to ten positive, unique, sorted quantities;
- no request body;
- no redirects; and
- no environment-derived proxy configuration.

There is no order, cancel, holding, transfer, arbitrary URL, arbitrary query, `POST`, `PUT`,
`PATCH`, or `DELETE` transport surface.

## Transport and response safety

The default client uses bounded connect, read, write, and connection-pool timeouts. Only the
documented safe-read transient conditions are retried:

- transport failure;
- HTTP `429`;
- HTTP `500`; and
- HTTP `503`.

There are at most three attempts. `Retry-After` is capped at five seconds. Exponential backoff and
jitter are bounded. HTTP `401` and `403` stop immediately and are never retried. Redirects,
unexpected statuses, bodies larger than 1 MB, invalid JSON, and strict-schema failures stop the
capture.

Exceptions identify only the endpoint and safe failure category. They never include a response
body, request headers, API key, signature, private key, account number, buying power, or invalid
input value.

The first authenticated preflight on 2026-08-17 established one narrow live-schema difference:
the v2 best-bid/ask row included an undocumented `timestamp` in addition to the officially sampled
`symbol`, `bid`, and `ask` fields. A pre-results compatibility amendment admits only this optional
field, requires timezone-aware UTC when present, and excludes it from persisted sanitized source
and all derivations. Every other unknown response field remains a hard schema failure. The failed
attempt wrote no evidence and exposed no market, fee, account, or strategy value in its sanitized
error.

After that compatibility amendment, two further attempts stopped on the unchanged semantic rule
that a buy `ask` must not be below a sell `bid`. Robinhood's official v2 component schema defines
the fields in those action directions. The safe errors exposed no values, the estimated-price
request was not reached, and the output directory remained absent. This is a live data-quality
stop: labels must not be swapped, prices must not be reordered with `min`/`max`, and the preflight
must not be forced to pass.

## One capture cycle

One cycle performs exactly four sequential reads:

1. accounts and fee tier;
2. the `BTC-USD` trading-pair contract;
3. `BTC-USD` best bid/ask; and
4. one `side=both` estimated-price request containing the four frozen quantities.

Before any evidence write, the collector requires:

- exactly one active API-tradable account;
- no unconsumed account or trading-pair pagination;
- exactly one matching trading pair;
- exactly one matching best-price row;
- exactly one bid and ask row for every frozen quantity; and
- no extra symbol, side, or quantity row.

It then constructs four in-memory G3.2c fixtures with shared response timestamps and validates all
four observations before the first write. The existing G3.2c writer redacts account number and
buying power and persists only immutable observation, sanitized-source, and manifest files.

## Preflight

The preflight is an explicit network action and is never run by installation or tests:

```bash
./market.sh preflight-rh-v2-cost \
  --authorization-reference AUTH-G3.2E-RH-READONLY-2026-08-17 \
  --credential-label g3-cost-study-v1 \
  --protocol config/research/rh-v2-cost-sampling-v1.json \
  --out-dir data/research/rh-v2-cost-preflight
```

The preflight passes only if all four endpoint schemas, account status, API tradability, fee
consistency, size constraints, timestamp constraints, arithmetic, four-quantity completeness,
redaction, immutable hashes, and deterministic rederivation pass. Its output directory is separate
from the production corpus and is never admitted to the 30-day analysis.

## Scheduled collection

A production run requires a future immutable run plan citing exactly
`AUTH-G3.2E-RH-READONLY-2026-08-17`. The per-cycle command performs network reads only when invoked
inside the one-minute admission window for exactly one scheduled slot:

```bash
./market.sh capture-rh-v2-cost-cycle \
  --protocol config/research/rh-v2-cost-sampling-v1.json \
  --run-plan PATH_TO_FROZEN_RUN_PLAN.json \
  --credential-label g3-cost-study-v1 \
  --out-dir PATH_TO_RUN_OBSERVATIONS
```

Before network contact, it atomically creates a slot-specific claim under
`.collector/RUN_ID/SLOT/started.json`. A successful attempt adds `completed.json`; a handled failure
adds a sanitized `failed.json`. A claimed slot is never attempted again, including after a partial
write or process crash. This preserves the preregistered missingness contract and prevents
selective retries or favorable backfill.

The command is deliberately one-cycle-at-a-time. A separately reviewed macOS scheduler may invoke
it around each slot after the preflight and dated plan pass. Scheduler installation and the 30-day
start are not implied by the collector implementation.

## Persisted and prohibited data

Persisted observation evidence may contain:

- account status and API-tradable flag;
- buying-power currency, but not buying power;
- fee ratio and 30-day volume;
- trading-pair increments and size limits;
- best and estimated prices;
- hypothetical estimated fees and totals;
- local receive and Robinhood estimate timestamps; and
- derived spread, size-impact, and all-in cost measures.

It must never contain:

- account number;
- buying power;
- API key;
- private or public signing-key material;
- request signature or authorization headers;
- Robinhood password, cookie, or two-factor code;
- response bodies in failure records; or
- an order, fill, holding, or transfer.

## Stopping boundary

G3.2e implementation readiness does not establish a credential, broker connection, empirical cost,
strategy result, or gate pass. The sequence is:

1. full offline QA and security review;
2. committed clean implementation;
3. local Keychain key preparation;
4. account-owner read-action confirmation in Robinhood;
5. local API-key completion and key-pair check;
6. one explicit read-only preflight;
7. preflight evidence review;
8. future run-plan freeze; and
9. separately reviewed scheduler activation.

Any failure stops at its stage. No failure unlocks an order path or permits relaxing the frozen
study rules.
