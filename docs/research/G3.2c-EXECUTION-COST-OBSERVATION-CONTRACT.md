# G3.2c Robinhood v2 Execution-Cost Observation Contract

- **Version:** 1.0
- **Date:** 2026-08-17
- **Status:** Offline contract implemented; no broker observation collected
- **Research role:** Input-design support for a prospective G3 protocol 2.0
- **Broker contact authorized by this contract:** None
- **Execution or order evidence produced:** None

## Purpose

Protocol 1.0 was retired before execution partly because its route-specific cost assumptions drove
the study's power. A successor protocol needs measured or explicitly estimated costs without
conflating displayed spread, order-size impact, exchange fee, and realized slippage.

This contract defines how a local JSON fixture shaped like official Robinhood Crypto Trading API
v2 read responses becomes a versioned, immutable cost-observation bundle. The implementation is
offline by construction. It does not implement HTTP, authentication, signatures, credentials,
orders, order history, or a background sampler.

The contract is reusable by any BTC strategy hypothesis. It contains no EMA signal, parameter,
return, trade, P&L, G1 candle, or holdout field.

## Official route semantics

The allowed source is Robinhood Crypto Trading API **v2**. Robinhood documents v2 as the version
with fee tiers and describes its best-price rows as prices across partner exchanges. The best
price excludes order size and fee and may differ from final execution. The v2 estimated-price
resource supplies quantity-aware bid and ask estimates, fee ratio, estimated fee, and estimated
total cost or credit; its bid and ask values exclude the fee.

This contract therefore labels every output:

```text
routing_model = partner_exchanges
measurement_type = hypothetical_estimate_not_execution
```

It must not be applied to v1 market-maker responses. V1 spread-inclusive routing remains a
different venue-cost profile.

Official references:

- [Robinhood Crypto Trading API documentation](https://docs.robinhood.com/crypto/trading/)
- [Robinhood Crypto API version overview](https://robinhood.com/us/en/support/articles/crypto-api/)
- [Robinhood crypto fee tiers](https://robinhood.com/us/en/support/articles/crypto-fee-tiers/)

## Complete read-resource allowlist

The source fixture may represent exactly these four v2 GET resources:

| Purpose | Method | Path |
|---|---|---|
| Account state and fee tier | `GET` | `/api/v2/crypto/trading/accounts/` |
| Pair constraints and tradability | `GET` | `/api/v2/crypto/trading/trading_pairs/` |
| Best displayed partner-exchange bid/ask | `GET` | `/api/v2/crypto/marketdata/best_bid_ask/` |
| Quantity-aware price and fee estimate | `GET` | `/api/v2/crypto/trading/estimated_price/` |

The code contains no request executor. `/orders/`, cancel, POST, PATCH, PUT, and DELETE resources
are absent from the allowlist. Even read-only order history is deliberately outside this narrow
cost-observation contract.

## Input fixture

Schema version 1 requires:

- source kind: `synthetic_fixture` or `captured_read_only_v2`;
- requested uppercase USD symbol and positive asset quantity;
- one official-response-shaped object for each allowlisted resource;
- a separate local UTC receive timestamp for each of the four responses; and
- both a `bid` estimate and an `ask` estimate for the exact symbol and quantity.

All models reject unknown fields. Decimal strings remain exact monetary values. Timestamps must
be timezone-aware UTC.

### Cross-response admission checks

Derivation fails closed unless all of the following hold:

1. Exactly one active, API-tradable account is present.
2. Exactly one matching trading pair and best bid/ask row are present.
3. Exactly one matching `bid` and one matching `ask` estimated-price row are present.
4. Account and both estimate fee ratios agree exactly.
5. The pair's asset and quote codes match the requested symbol.
6. The pair is API-tradable; quantity respects its asset increment, is strictly below its maximum,
   and clears its quoted-currency minimum at the displayed midpoint.
7. Best and estimated asks are not below their corresponding bids.
8. The four local response receive times span no more than 60 seconds.
9. The estimated-price server timestamp is at most 60 seconds old at local receipt and no more
   than 5 seconds in the future.
10. Buy total cost is consistent with estimated ask notional plus fee, and sell total credit is
    consistent with estimated bid notional minus fee, to a maximum retained residual of $0.02.

These are observation-admission rules, not claims that a hypothetical estimate will equal a later
execution.

## Derived measures

Let best bid be `B`, best ask be `A`, midpoint be `M = (A + B) / 2`, quantity be `q`, estimated
size-aware ask and bid be `Ae` and `Be`, estimated fee be `F`, and estimated total cost/credit be
`TC` and `TR`.

The bundle retains rather than merges:

```text
displayed full spread bps = (A - B) / M * 10,000

buy displayed half-spread cost bps = (A / M - 1) * 10,000
buy size impact bps = (Ae / A - 1) * 10,000
buy effective all-in price = TC / q
buy all-in one-way cost bps = (TC / q / M - 1) * 10,000

sell displayed half-spread cost bps = (1 - B / M) * 10,000
sell size impact bps = (1 - Be / B) * 10,000
sell effective all-in price = TR / q
sell all-in one-way cost bps = (1 - TR / q / M) * 10,000
```

Fee ratio, fee bps, estimated fee dollars, gross estimated notional, total dollars, and arithmetic
residual are stored for both directions. The indicative round-trip figure is the sum of the two
midpoint-relative one-way figures from the same admitted capture cycle.

That sum is a comparable research diagnostic. It is not an executed round trip, a fill forecast,
or a substitute for later realized-slippage evidence.

## Evidence bundle

`derive-rh-v2-cost` writes a new content-addressed directory:

```text
rh-v2-cost-YYYYMMDDTHHMMSSZ-<16 hex>/
  manifest.json
  observation.json
  source.sanitized.json
```

The manifest binds the observation and sanitized source by SHA-256 and byte count. An existing
observation directory is never overwritten. Verification reparses both strict schemas, checks both
hashes and sizes, rederives the observation from the sanitized source, and requires exact equality.

Before persistence, account numbers, account buying power, API keys, signatures, authorization
values, and private-key fields are redacted. Fixture headers or other unknown top-level fields are
rejected. The committed synthetic fixture contains an intentionally recognizable fake account
number so the redaction test proves it never appears in output.

## Commands

The committed fixture is synthetic and exists only for contract tests:

```bash
./market.sh derive-rh-v2-cost \
  --fixture tests/fixtures/robinhood/v2_cost_snapshot.json \
  --out-dir /tmp/market-rh-v2-cost

./market.sh verify-rh-v2-cost \
  --manifest /tmp/market-rh-v2-cost/OBSERVATION_ID/manifest.json
```

The command names, help, console output, manifest, and observation all identify the operation as
offline or hypothetical. Running them cannot contact Robinhood.

## Current interpretation and next authorization boundary

The synthetic fixture's numbers are a hand-calculated golden case, not a measurement of the user's
account or current market. They cannot set a protocol 2.0 cost assumption or support strategy
promotion.

A real observation program still requires a separate decision covering credential scope, official
signing, read transport, sampling cadence, retention, rate limits, clock checks, and operational
security. The controlling roadmap currently forbids creating a Robinhood credential while G3 is
unresolved. This offline increment does not change that lock and does not mark G5 complete.
