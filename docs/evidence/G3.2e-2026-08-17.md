## Outcome

The repository now contains the minimum authenticated, read-only Robinhood v2 path required to
produce future G3.2d execution-cost observations. It includes a macOS-Keychain-backed credential
lifecycle, Robinhood's documented Ed25519 signature construction, an exact fixed-origin and
GET-only endpoint allowlist, bounded safe-read retries, strict response validation, sanitized
errors, multi-quantity cost capture, preflight CLI, and scheduled-slot claiming.

The initial implementation checkpoint used only synthetic fixtures and an in-process HTTP mock
transport. Post-commit work then created and locally verified the authorized least-privilege
credential and invoked the explicit live preflight. Authentication succeeded, but strict
best-price validation stopped every attempt before the estimated-price request or first evidence
write. Therefore this record establishes credential and fail-closed transport behavior, but no
account-specific cost value.

## Credential boundary proved offline

- Ed25519 signing seeds are generated with PyNaCl.
- Private seed, public key, and issued API key use separate macOS Keychain service identifiers.
- The runtime checks that the active `keyring` backend is the macOS backend.
- API keys and private keys are not accepted from environment variables, `.env`, command-line
  arguments, file paths, fixtures, or config.
- Key preparation returns and prints only the public key and SHA-256 fingerprint.
- API-key completion uses a hidden interactive prompt and prints only the credential label and
  public-key fingerprint.
- Existing labels are never overwritten by lifecycle commands.
- The stored public key is compared with the public key derived from the stored private seed.
- Credential object representations replace API and private keys with `[REDACTED]`.
- Malformed-secret errors contain only stable error categories and never echo input.
- The locally installed backend resolved to `keyring.backends.macOS.Keyring`.

The initial implementation-readiness test run used an in-memory fake store and performed no real
Keychain write. The later authorized setup created the private-seed, public-key, and API-key items
under credential label `g3-cost-study-v1`; no secret value was printed or persisted in this record.

## Authentication and transport proved offline

The published Robinhood example produces its exact documented signature:

```text
q/nEtxp/P2Or3hph3KejBqnw5o9qeuQ+hYRnB56FaHbjDsNUY9KhB1asMxohDnzdVFSD7StaTqjSd9U9HvaRAw==
```

The test retains the official example's Python `str(body)` representation exactly. Production
G3.2e requests are bodyless GETs and therefore do not depend on request-body serialization.

The mock transport verifies that the signature covers the exact path and query emitted by HTTPX,
including the literal, ordered four-quantity list. The production client:

- fixes `https://trading.robinhood.com` as its origin;
- admits `BTC-USD` only;
- exposes accounts, one trading pair, best bid/ask, and estimated price only;
- accepts no arbitrary method, URL, path, body, account number, or query dictionary;
- has no public `request`, `post`, `place_order`, cancel, holding, order-history, or transfer method;
- sets `trust_env=False`, forbidding environment-derived proxies;
- forbids redirects;
- caps response bodies at 1 MB;
- preserves JSON decimal values with Decimal parsing;
- validates responses under strict G3.2c Pydantic models;
- retries only transport failure and HTTP `429`, `500`, or `503`;
- makes at most three attempts;
- caps `Retry-After` at five seconds; and
- never retries HTTP `401` or `403`.

Response-body values are excluded from transport, authorization, JSON, and schema errors. A test
places a sensitive-looking account identifier in an invalid response and proves it is absent from
the resulting exception.

## Collector and missingness behavior proved offline

One synthetic cycle makes four logical reads and receives all four frozen quantities in one
estimated-price response. Before the first evidence write, the collector rejects:

- a protocol other than `rh-v2-cost-sampling-v1`;
- a source contract other than `captured_read_only_v2`;
- account or pair pagination;
- zero or multiple active API-tradable accounts;
- missing, duplicate, or extra pair/best-price rows;
- missing, duplicate, or extra symbol/side/quantity estimated-price rows; and
- any G3.2c size, timestamp, fee, arithmetic, tradability, or redaction failure.

The success test writes four content-addressed G3.2c bundles. Each re-verifies and contains
`[REDACTED]` for account number and buying power. No authentication header or credential field is
present.

A scheduled attempt must cite exactly `AUTH-G3.2E-RH-READONLY-2026-08-17` and fall between one
scheduled slot and its inclusive 60-second lateness boundary. It atomically claims that slot before
calling the client. A simulated authorization failure writes a sanitized failure code. A second
attempt at the same slot is rejected before the client is called. This proves no same-slot retry or
selective backfill path exists.

## Official-source check

The design was checked against current official Robinhood documentation on 2026-08-17:

- authenticated requests require `x-api-key`, `x-signature`, and `x-timestamp`;
- signatures use the private key, API key, timestamp, path, method, and body;

## Decision and next stopping point

Record `G3.2e: CREDENTIAL READY — LIVE PREFLIGHT BLOCKED ON BEST-PRICE COHERENCE`.

Do not record G3.2e as passed, do not create the production run plan, and do not start the 30-day
window. Robinhood's official v2 component schema defines `bid` as the best partner-exchange price
for a sell order and `ask` as the best price for a buy order. The live responses repeatedly failed
the required `ask >= bid` relationship. Swapping labels, taking `min`/`max`, admitting a negative
spread, or otherwise changing the estimand after contact is prohibited.

The next admissible step is a separately reviewed resolution of the venue/API contradiction—for
example, authoritative Robinhood clarification or a prospectively specified diagnostic sample—then
a fresh sanitized preflight under the unchanged cost estimand. No step authorizes an order,
transfer, holdings change, strategy result, or live capital.

That next-step decision is now frozen in
`docs/research/G3.2e-BEST-PRICE-COHERENCE-RESOLUTION.md`. Its support draft has not been submitted,
and its sign-only fallback has no implementation or network authority.

## Authenticated preflight chronology

After the implementation-readiness commit, the account owner created a replacement credential
named `market-g3-cost-study-v1` and visibly confirmed that only Read crypto accounts, Read crypto
products, and Read crypto quotes were enabled. Both order actions, holdings reads, and order-history
reads were disabled. The private signing seed and issued API key were stored separately in macOS
Keychain, and the local sign/verify pairing check passed without network contact or secret output.

The first explicit preflight attempt then authenticated successfully for the accounts and trading
pair reads but stopped on strict validation of the best-bid/ask response. The safe error reported an
extra `results[0].timestamp` field; it contained no response value. Because the collector validates
all four responses before the first write, no preflight evidence directory or partial cost
observation was created.

Robinhood's official v2 response sample showed only `symbol`, `bid`, and `ask`, while the live row
added `timestamp`. Before any cost observation was available, the parser was amended to admit only
that optional field, require timezone-aware UTC, and exclude it from sanitized persistence and all
derivations. All other unknown response fields remain forbidden. This is a transport-compatibility
amendment, not a change to the frozen endpoint set, quantities, schedule, estimand, or study gate.

After that narrow amendment, two further attempts reached semantic validation of the same
best-price row and stopped because the buy `ask` was below the sell `bid`. The safe errors contained
only the endpoint, field location, and validation category; they contained no price, spread, fee,
account identifier, buying power, or credential. The official schema bundle describes the fields
as sell-order bid and buy-order ask, so the existing ordering invariant was retained. The
estimated-price endpoint was not reached, the output directory remained absent, and no empirical
cost observation exists.
