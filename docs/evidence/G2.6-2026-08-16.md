## Implemented contract

The backtester now uses distinct, noninterchangeable lifecycle units:

| Unit | Definition |
|---|---|
| Order | One risk-accepted strategy request or terminal-liquidation request |
| Execution | One fill; an order may have zero, one, or multiple executions |
| Partial-fill execution | One execution smaller than its parent order's requested quantity |
| Closed trade | One sell execution that reduces positive inventory and realizes matched P&L |
| Round trip | One complete flat-to-positive-inventory-to-flat cycle |
| Open round trip | A cycle that entered positive inventory but has not returned to flat |

Orders aggregate executions by client order ID. Their terminal lifecycle state is `filled`,
`partially_filled`, `expired`, `execution_rejected`, or `unfilled`. A partially filled order can
also retain the disposition of its unfilled remainder. Aggregate executions cannot exceed the
requested quantity, and every execution must reconcile exactly to its G2.5 journal entry.

## Fee-aware trade outcomes

Each inventory-reducing sell execution creates one closed-trade record using weighted-average
basis and an exact proportional allocation of remaining entry fees:

```text
allocated entry fees = unallocated entry fees * sold quantity / pre-sell inventory
net realized P&L     = sell notional - allocated gross basis
                       - allocated entry fees - exit fee
```

The closed trade is a win when this net value is positive, a loss when negative, and breakeven
only when it is exactly zero. Round-trip P&L independently sums all entry notionals and fees and
all exit notionals and fees between the flat boundaries.

## Hand-calculated multi-execution proof

The principal fixture contains two parent orders and four executions:

| Parent order | Execution | Notional | Fee |
|---|---|---:|---:|
| Buy `2 BTC` | Buy `1 @ $100` | `$100` | `$1.00` |
| Buy `2 BTC` | Buy `1 @ $110` | `$110` | `$1.10` |
| Sell `2 BTC` | Sell `1 @ $120` | `$120` | `$1.20` |
| Sell `2 BTC` | Sell `1 @ $90` | `$90` | `$0.90` |

The lifecycle result is exactly:

```text
orders                  = 2
executions              = 4
partial-fill executions = 4
closed trades           = 2
round trips             = 1
open round trips        = 0
open inventory          = 0 BTC
```

Weighted-average gross basis is `$105` per BTC and allocated entry fees are `$1.05` per BTC. The
first exit realizes `$15` gross and `$12.75` net after entry and exit fees, so it is one win. The
second realizes `-$15` gross and `-$16.95` net, so it is one loss. Closed-trade and round-trip net
P&L both reconcile to `-$4.20` without treating four executions as four orders or round trips.

## Artifact contract

Schema version 8 adds `lifecycle.jsonl` with:

- one lifecycle summary;
- one record per order, including requested, executed, and remaining quantity and terminal state;
- one record per closed trade, including allocated basis, allocated entry fee, exit fee, net P&L,
  and outcome; and
- one record per completed flat-to-flat round trip.

The summary JSON and CLI separately report order, execution, partial-fill, closed-trade,
win/loss/breakeven, round-trip, and open-inventory metrics.

## Failure-path coverage

- Duplicate order IDs, nonpositive/non-finite requested quantities, unknown dispositions, fills
  for unknown orders, and fill sides that disagree with the request fail closed.
- Aggregate execution quantity greater than requested quantity fails closed.
- A fully filled order cannot also carry an unfilled disposition.
- Fill count or content that does not exactly match the immutable accounting journal fails closed.
- A sell greater than lifecycle inventory fails closed.
- Final lifecycle inventory and gross basis must match the final journal state.
- Partially filled, expired, execution-rejected, open-inventory, win, loss, and fee-aware breakeven
  paths all have deterministic coverage.
